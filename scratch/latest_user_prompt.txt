3. DENTIST AVAILABILITY MODULE
============================================================

Implement secure CRUD for DentistAvailability.

Required behavior:

A. CREATE AVAILABILITY

Only an authenticated dentist may create availability.

The dentist must:

- Have role = dentist.
- Be active.
- Have verification_status = approved.
- Create availability only for themselves.

The client must NOT be able to provide or override:

- dentist_id
- created_at
- updated_at

The dentist identity must be derived server-side from the authenticated
Firebase user and database relationship.

Validate:

- weekday/day-of-week
- start time
- end time
- active/inactive state where supported by the existing model

Reject invalid time windows where:

start_time >= end_time

Prevent inappropriate overlapping availability records where required
by the existing model/business rules.

B. READ AVAILABILITY

Patients must be able to read appropriate dentist availability for
appointment discovery.

Dentists may read their own availability.

Dentists must NOT be able to modify or access another dentist's private
availability through ownership bypass.

Admins may inspect availability according to existing admin authorization.

C. UPDATE AVAILABILITY

Only the owning approved/active dentist may modify their availability.

Do not allow a dentist to modify another dentist's record.

Validate all updated time/day fields.

Preserve server-controlled timestamps.

D. DELETE AVAILABILITY

Only the owning approved/active dentist may delete their availability.

Prevent cross-dentist deletion.

Audit the deletion.

6. AVAILABILITY ENFORCEMENT
============================================================

Before creating an appointment:

1. Verify the dentist exists.
2. Verify dentist is active.
3. Verify dentist is approved.
4. Determine the requested appointment date/time.
5. Determine the corresponding weekday.
6. Verify that the requested appointment falls within the dentist's
   configured availability.
7. Reject appointments outside availability.

Use the existing Appointment model fields and existing availability
structure.

Do not invent unsupported scheduling semantics.
